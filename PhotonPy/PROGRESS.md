## 3. Python-клиент Photon (photon0509.py)

Единый модуль (только stdlib): параметры билда, Protocol18, UDP EnetPeer
(sync `PhotonUdp` + async `AsyncPhotonUdp`), сборка фрагментов, разбор комнат.

### Исправленные баги

1. **Главный: авторизация на игровом сервере.**
   Было: после CreateGame на мастере клиент закрывал соединение и логинился на GS
   своим HMAC (`224/220/223/225/217/216`). Комната создавалась (`rc=0`), но **в лобби
   не публиковалась**.
   Стало: GS-сессия логинится **токеном мастера** (параметр `221` из ответа на
   CreateGame), и только потом отправляет CreateGame. Комната сразу появляется в лобби.

   ```python
   await master.send_operation(create_payload)
   gs_addr = parse_simple_string(resp, 230)
   token   = parse_simple_string(resp, 221)
   await gs.connect()
   await gs.send_operation(build_op(230, (221, token)))   # ключевой момент
   await gs.send_operation(create_payload)
   ```

2. **Счётчик записей Hashtable.** После добавления свойства `OnlyModUsers` счётчик
   остался 16 при 17 записях → сервер молча перестал отвечать на CreateGame.
   Исправлено (17).

3. **Zigzag для int (типы 9/10).** Не декодировался: `max` показывался вдвое больше,
   `GameMode` — как 4 вместо 2. Теперь `(v >> 1) ^ -(v & 1)`.

4. **ACK.** Подтверждались только команды с флагом reliable → сервер бесконечно
   повторял `event 226` каждые 5 с. Теперь ACK шлётся на любую команду с `seq != 0`,
   кроме ACK/PING.

5. **StringArray (тип `0x47`).** Не разбирался → десинхронизация при чтении
   `GameProperties` (список свойств для лобби).

6. **Async-клиент терял сообщения.** `receive_timeout()` возвращал только первое
   сообщение датаграма, остальные (в т.ч. ответ на CreateGame) терялись. Добавлена очередь.

7. **Дубли uid.** Сервер держит одну сессию на `UserId` (`CheckUserOnJoin`): второй
   клиент с тем же uid выкидывает первый. Для тестов держатель и проверяющий должны
   иметь разные uid.

8. **Сервер не регистрирует новые uid** (`rc=-2689` / `32757 "Too many accounts from
   this address"`). Рабочее решение: стабильный `photon_uid.txt` + фолбэк на известный
   uid `bc57d040…` (сохраняется автоматически).

## 5. План (что делаем сейчас)

1. Зайти с телефона в комнату `PyTest` (создана Python-клиентом, 2 игрока, FlatGrass).
2. Поставить в комнате **один монитор** (`PcMonitor`) — это делает хост, т.е. телефон.
3. `watch_spawns.py` ловит RPC-спавн, вытаскивает `view id` монитора.
4. Python раз в 3 секунды шлёт новый цвет (`build_monitor_sync_payload` +
   `SetTextWithoutController`), параллельно снимаем экран телефона.
   **Критерий успеха:** цвет монитора на скриншотах реально меняется.
5. Если работает — масштабируем: сетка мониторов, поток кадров из видео
   (`Optimized.py` уже умеет генерировать текст из кадров: 6×2 «пикселя» на монитор,
   цвет блока — `#RGB` с квантованием 4 бита).

### Справочно: формат монитора

- Проп `PcMonitor` (есть также `OldMonitor`), изначально чёрный прямоугольник с рамкой.
- Экран — rich-text из блоков `█`, каждый со своим `<color=#RGB>`; текст оборачивается
  в `<size=136%>` и `<b>`.
- Состояние монитора передаётся потоком OnSerialize (event 206):
  `[view_id, ..., pos, rot, ..., isKinematic, signal, connectedIds.Count, text, color]`.
- Управление: `MonitorController` (instantiationData `Text`/`Background color`,
  `connectedIds = [monitor]`) либо RPC `SetTextWithoutController`.

## 7. Настоящий монитор — `Monitor`, а не `PcMonitor` (16.11.2026)

Разбор префабов 0.5.0.9:

- `Resources/props/resources/PcMonitor.prefab` и `OldMonitor.prefab` — только железо:
  меш `OP1_Monitor_v1`, `PhotonView`, `Rigidbody`, `Prop`, `PhotonTransformView`.
  **Экрана у них нет** — поэтому на телефоне был чёрный «кирпич».
- Настоящий экран — wire-компонент **`Monitor`**
  (`Resources/wire/resources/Monitor.prefab`): `PhotonView` + `PhotonTransformView` +
  `Monitor` + world-space `Canvas` (`Image background` + `Text`, 1022x511, шрифт 48,
  scale 0.0025) + LOD (`Canvas` включается в радиусе 40 м от камеры).
- `MonitorController` — маленький контроллер (`text`, `color`), толкает текст в монитор
  через `connectedIds`; для прямой трансляции не обязателен.
- Скрипт `Monitor` (TypeDefIndex 5593): `SetTextWithoutController` (RPC),
  `GetRuntimeData`/`ApplyRuntimeDictionaryValues`, `OnPhotonSerializeView` —
  поэтому состояние экрана шлётся обычным event 206.

### Ориентация

Экран смотрит по локальной **-Z**. Для игрока, стоящего с +Z (стандартный спавн
FlatGrass), правильный поворот — `(x=0, y=1, z=0, w=0)` (y180).
Проверено вручную по 5 мониторам:

| поворот | что видно |
|---|---|
| identity | задняя стенка (тёмная) |
| x+90 / x-90 | экран плашмя, виден с ребра |
| x180 | экран к нам, но перевёрнут вверх ногами |
| **y180 (0,1,0,0)** | **правильно: экран к нам, ориентация верная** |

### Проверка «живого» цвета

Один `Monitor`, цвет меняется каждые 3 с; замер пикселя экрана на телефоне:

| время (python) | цвет в логе | RGB на экране |
|---|---|---|
| 08:31:15 | green `#0F0` | (79, 222, 79) |
| 08:31:19 | blue `#00F` | (80, 83, 219) |
| 08:31:22 | yellow `#FF0` | (219, 222, 79) |
| 08:31:25 | red `#F00` | (220, 83, 79) |

## 8. Ёмкость экрана монитора (калибровка)

Тег `<size=N%>` реально масштабирует rich-text. Калибровочная сетка (разные цвета

## 10. Поздние игроки, keep-alive и чужие

1. **Поздний гость не получает объект, заспавненный до него.** Photon кэширует
   события, но объект у клиента не появляется → монитор спавнится **на каждый вход**
   (в `monitor_video.py`), с новым view id.
2. **Без пингов комната исчезает из лобби через ~10 с.** `hold_room.py` пинговал,
   а `rot_test.py`/`monitor_test.py` — нет, поэтому комната «пропадала».
   Теперь `send_ping()` каждые 3 с во всех циклах.
3. **Список серверов обновляется на лету**, если фильтр уже введён. Значит можно
   заранее набрать имя, создать комнату и войти через 1-2 с.
4. **Пароль.** Свойство `Password` нужно добавить в список лобби-свойств
   (параметр 250 в GameProperties), иначе клиент игры его не видит:
   нет замка и нет запроса пароля. С ним появляется 🔒 и панель ввода.
   Сервер пароль не проверяет — это клиентская логика игры.
5. **Кик чужого** (PUN CloseConnection): `RaiseEvent` 203, data = actor,
   адресат — `ActorList` (252) = [actor]. В нашей проверке клиент игры его
   проигнорировал; основной барьер — пароль.

## 12. Стена мониторов и максимум пикселей на монитор (16.11.2026)

### Сколько пикселей реально влезает в один `Monitor`

Калибровка белой рамкой (рамка = край сетки), экран монитора 650x384 px при scale 0.0025:

| сетка | рамка на экране | вывод |
|---|---|---|
| 12x8 @50 | 49x39 px | ~60% ширины — крупные чёрные поля по бокам |
| 16x10 @50 | 66x39 px | ~80% |
| **18x12 @50** | **75x43 px** | **почти весь экран (~76x44) — рабочий максимум** |
| 19x13 @50 | 75x39 px | обрезается по высоте |
| 20x12 @50 | 75x39 px | переносится/обрезается (видно по «рваной» рамке) |

Итог: **18x12 = 216 блоков на монитор при `<size=50%>`**. Тег `<size>` работает:
136% -> 6 колонок, 100% -> 8, 50% -> 18.

### Стена

Геометрия из `Optimized.py`: шаг мониторов **1.73 x 1.06** world units
(экран 1.625 x 0.96 + зазор). Мониторы ставятся в сетку `cols x rows` вокруг
точки (`--cx`, `--cy`, `--cz`).

Каждый монитор показывает свой кусок кадра, поэтому картинка стыкуется.
Проверено:

| стена | пикселей | объектов | fps телефона |
|---|---|---|---|
| 2x2 | 36x24 | 4 | ~29 |
| 3x3 | 54x36 | 9 | ~10 (fps 3) |
| 4x3 | 72x36 | 12 | 12 (fps 2.5) |
| 5x3 | 90x36 | 15 | 42 (fps 2) |
| **5x4** | **90x48** | **20** | **60 (fps 2)** |

Лимит комнаты — **1000 объектов**; у нас 1 объект на монитор (20 из 1000).
Дальше ограничивают не объекты, а FPS телефона и полоса Photon
(на монитор ~5.5 КБ на кадр, 18x12 при `<size=50`).

### Оптимизации стены

1. **Шлём только изменившиеся плитки** (`last_text` на монитор) — в монотонных
   сценах трафик падает почти до нуля, поэтому 20 мониторов держат 60 fps.
2. **Пауза 30 мс** между мониторами в кадре — иначе 20 больших событий подряд
   теряются в UDP.
3. Цвета в тексте — 3 hex-цифры (`<color=#RGB>`), как в `Optimized.py`.
4. Кик чужих теперь **выключен по умолчанию** (`--kick`): после реконнекта
   телефон получал новый actor и выкидывался. Барьер — пароль комнаты.

### Запуск

```
ffmpeg -i video.mp4 -an -vf "scale=90:48:flags=neighbor,fps=2" \
       -f rawvideo -pix_fmt rgb24 monitor_90x48.rgb

python monitor_video.py --room Wall8 --cols 5 --rows 4 --w 18 --h 12 \
       --size 50 --fps 2 --password 1234 --cy 2.13 --start-sec 130 \
       --rgb ..\video\monitor_90x48.rgb

python phone_join.py --room Wall8 --password 1234
```

`--start-sec 130` — начать с середины ролика (4:26, кадры 4 fps/2 fps зависят
от `--fps`; смещение считается как `start_sec * fps`).

### Практические детали

- 5x4 при `cy=2.13`: нижний ряд на y=0.54 (над землёй), верхний на y=3.72.
- Между мониторами остаются тонкие чёрные швы (безель + поля текста ~4%),
  картинка при этом читается как единая.
- Если понадобится больше: следующий шаг 6x4 (108x48) или 6x5 (108x60),
  но следить за fps телефона (падает ниже ~10 — уже не смотрится).

## 13. Почему стена оставалась чёрной (17.11.2026)

Симптом: одиночный `Monitor` и маленькие стены (3x3, 5x4) рисуют видео,
а 6x5 (30 объектов) и 7x5 (35) — полностью чёрные. В логе при этом
`m0 sent ok=True` и меняющийся CRC, т.е. события уходят.

### Причина 1 — большие события не фрагментировались

`PhotonUdp.send_op()` отправлял payload одним reliable-пакетом. Текст одного
монитора 18x12 = ~4.6 КБ, датаграмма ~4.7 КБ → IP-фрагментация (4 пакета),
потеря любого фрагмента = потеря всего события, а ретрансмита у нас нет.
При 20 мониторах ещё «пролезало», при 30-35 — нет.

Фикс: штатная фрагментация Photon (команда типа 8, как `MTU=1200` в SDK):

```
[type=8][channel][flags][0x04][size u32][seq u32]
[startSeq u32][fragmentCount u32][fragmentNumber u32][totalLen u32][offset u32][data]
```

Максимум данных в фрагменте: `MTU - 12 (датаграмма) - 12 (команда) - 20 (фрагмент)`
= 1156, используем этот же расчёт в коде.

### Причина 2 — плотная пачка спавнов теряется

`Instantiate`-события спавна мелкие, но если 30 штук приходят подряд,
диспетчер игры падает с `NullReferenceException` / `IndexOutOfRangeException`
(`DispatchIncomingCommands`) и остаток пачки не обрабатывается — часть стены
просто не появляется (наблюдали 2 и 5 объектов из 30).

Фикс: пауза между спавнами `--spawn-gap-ms` (по умолчанию 250 мс).
30 мониторов = ~7.5 с сборки, зато появляются все.

## 14. Потеря событий: фрагментация + подтверждения (18.11.2026)

Симптом: стена из 30-35 мониторов показывала только 1-5 мониторов, остальные
оставались чёрными, хотя в логе `sent ok=True` и CRC менялись. Иногда не
появлялись даже сами объекты (2 из 35).

### Что оказалось

1. **Датаграммы больше MTU.** Текст монитора 18x12 ~4.6 КБ уходил одним
   reliable-пакетом => IP-фрагментация, потеря любого фрагмента = потеря
   события. Добавлена штатная фрагментация Photon (тип команды 8, MTU 1200,
   заголовок startSeq/count/number/totalLen/offset).

2. **Не обрабатывались подтверждения.** Photon подтверждает reliable-команды
   (тип 1), но наш клиент их игнорировал, поэтому потерянное событие исчезало
   навсегда. Теперь:
   - `PhotonUdp.pending[seq] = (cmd, ts, tries)` при каждой reliable-отправке;
   - входящие ACK вычищают очередь (`_absorb_ack` / `drain_acks`);
   - `retransmit()` повторяет неподтверждённое (каждые 350 мс, до 8 попыток).

3. **Спавн во время экрана загрузки.** Клиент игры выбрасывает instantiate-
   события, пришедшие пока он грузит карту: из 35 объектов появлялись 2.
   Добавлено ожидание `--ready-sec` (по умолчанию 20 с) после входа игрока,
   плюс `--spawn-gap-ms` (250 мс) между мониторами. Внутри
   `load_save_from_file` убрана лишняя пауза 0.5 с (нужна только при
   соединении wire-компонентов).

4. **Пакетная отправка.** После каждой 4-й панели (в кадре) выполняется
   `drain_acks()` + `retransmit()`; это же делается после полного кадра.

### Проверено на CPH2083 (18.11.2026)

| Стена | Пиксели | fps аргумент | Итог на телефоне |
|---|---|---|---|
| 7x5 (35) | 126x60 | 2 | вся стена с картинкой, 3-7 fps |
| 14x10 (140) | 252x120 | 1 | вся стена с картинкой, 4 fps, ~0.7 кадра/с |

- 140 мониторов = ~644 КБ на кадр. При fps 4 это 2.6 МБ/с — канал не тянет,
  реальный темп выходит меньше заявленного. Для 14x10 ставить `--fps 1`,
  для 7x5 — `--fps 2`.
- Стена 14x10 шириной 24 м целиком в кадр не влезает (это уже про обзор, не
  про сеть) — смотреть приходится поворачиваясь.
- Чёрная нижняя полоса на стене 14x10 — это letterbox самого видео, не баг.

### Скриншоты с телефона

`adb shell screencap -p /sdcard/x.png` + `adb pull` — единственный надёжный
способ. `adb exec-out screencap > file` из PowerShell портит PNG, а спящий
экран даёт полностью чёрный снимок (перед тестом: `input keyevent 224`,

## 15. Лимиты комнаты: 1000 предметов / 40 машин (18.11.2026)

В `GameProperties` комнаты есть `MaxProps` и `MaxVehicles` (в панели паузы
показываются как «Предметы: N/MaxProps» и «Транспорт: N/MaxVehicles»).

- Добавлены параметры `build_simple_hashtable(..., max_props=1000, max_vehicles=40)`
  и флаги `--max-props` / `--max-vehicles` в `monitor_video.py`.
- Баг: в `write_compressed_int` двухбайтовые варианты (типы 13/14) писались
  big-endian, а игра читает little-endian. Из-за этого `1000` (0x03E8)
  отображалось как `59395` (0xE803). Значения < 256 шли одним байтом,
  поэтому `MaxVehicles=40` работало, а `MaxProps=1000` — нет.
- Исправлено на little-endian; проверено на телефоне: панель паузы показывает
  **«Предметы: 0 /1000», «Транспорт: 0/40»**.

## 16. Скорость стены и старт с середины (18.11.2026)

- Задержки в коде, которые тормозили кадр, уменьшены: \--gap-ms\ 20 -> 5 мс,
